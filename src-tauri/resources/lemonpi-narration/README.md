# LemonPi narration

First-party Pi extension bundled with LemonPi. It adds visible narration and supervisor/worker orchestration contracts to every Pi turn, defaults top-level `pi-subagents` delegations to background execution, and requests one guarded repair response if a run settles after tool activity without a closing explanation.

The async policy uses the public mutable `tool_call` extension hook and the package's existing `async` option. It does not patch or fork `pi-subagents`, and it never invents child wall-clock timeouts. Main Pi is kept interruptible: LemonPi blocks `subagent_wait` and requires Main Pi to end its turn after dispatching and narrating active work. Package completion events normally wake integration; Command Center also watches for a run crossing from active into `complete`, `failed`, `stopped`, or `rejected` and sends a delayed private fallback wake if the package delivery path did not claim that terminal occurrence. Progress/status polling never wakes Main, historical terminal runs are baselined without waking, and a resumed run is re-armed when it becomes active again. A child remains alive between Main Pi turns, so a new user message can receive an immediate supervisor response and be turned into direct steering.

Dispatch is risk- and scope-based rather than file-count-based, but Main Pi is always a read-only orchestrator. Bounded low-risk work uses a single-executor fast path. Broader work is divided into ordered, independently reviewable vertical chunks. Every implementation handoff must name the chunk outcome, in-scope work, observable completion condition, and explicit out-of-scope remainder. LemonPi intentionally does not hard-code a provider, model, or custom specialist name.

Role selection is dynamic. Once per new user task, Main Pi must call `subagent({ action: "list" })` and use the returned executable roster as the authoritative capability registry. That public package API exposes the exact runtime names and descriptions of built-in, packaged, user, and project agents. Main Pi considers every listed agent and selects the best match autonomously, so custom agents are first-class without LemonPi encoding their names. Planner is the normal preparation role for multi-chunk, cross-subsystem, architecture-heavy, or ambiguous work; one-chunk changes skip it. Every specialist must answer a concrete question that changes the next decision, so broader role usage does not recreate ceremonial pipelines.

Main Pi cannot impose per-dispatch wall-clock, turn, tool, or usage budgets. LemonPi strips `timeoutMs`, `maxRuntimeMs`, `turnBudget`, `toolBudget`, and `usageBudget` from generated single, chain, and parallel launches before `pi-subagents` validates them. Work is bounded through task decomposition and activity-based intervention instead of guessed counters. Budget defaults deliberately configured by the user in package settings or an agent profile still apply because they are resolved by `pi-subagents` after the sanitized call.

Every delegated task and resume message receives a concise child-checklist contract. LemonPi equips installed built-in agents with the required `todo` tool/provider before Pi starts, and Command Center reads the plugin's structured tool-result snapshots from each child transcript to render that agent's own Tasks section. If an active async child has meaningful activity but still exposes no checklist after 30 seconds, Command Center sends one direct reminder to that child; it does not invent task state or repeatedly interrupt the same run attempt. Custom agents with an explicit tool allowlist remain user-owned and must list `todo`; agents without a strict allowlist inherit the provider normally.

The extension mechanically blocks Main Pi's file-editing tools and common shell-based project mutations while leaving inspection, search, tests, builds, status checks, and git-management operations available. Any executable agent selected from the live roster may own an implementation chunk when its declared role matches; LemonPi applies the same bounded chunk contract and single-writer guard without keying behavior to that agent's name. Corrections should steer or resume the same writer whenever possible.

Reviewers and other specialists are optional tools, not pipeline stages. An independent reviewer requires an explicit user request, a material risk boundary, or a concrete `Review justification: ...`; LemonPi mechanically blocks ceremonial review calls and blocks a second reviewer pass unless the user explicitly requested multiple reviews. Delegations without explicit runtime verification disable `pi-subagents`' automatically inferred structured acceptance report because Main Pi owns integration and validation. Only blocker-level findings justify a repair pass, and Main Pi validates that repair directly instead of creating a review-repair-review loop.

Acceptance configuration is preflighted before a worker launches. LemonPi defaults unspecified acceptance to `none` so `pi-subagents` cannot infer a post-run gate that Main Pi did not configure. Explicit `verified` acceptance is allowed only with at least one well-formed runtime `verify` command; merely asking the worker to run tests or report validation does not satisfy the package API. A malformed verified contract is blocked immediately without consuming a worker run.

The runtime permits sequential chunks but prevents overlapping writers: only one writer may own the shared checkout at a time, even if the user sends another message while it is working. Writer ownership is released from `pi-subagents`' structured `subagent:async-complete` lifecycle event keyed by the exact run id; human-readable completion text is only a compatibility fallback. After a completed chunk Main Pi inspects the diff, checks its stated acceptance condition, reports the checkpoint, and then dispatches the next bounded chunk with updated context. Two consecutive failed chunks stop automatic retries so repeated failure becomes an explicit blocker instead of an invisible loop. Parallel writers require explicit isolated worktrees.

`needs_attention` is treated as an intervention request rather than a healthy running state. The package wakes Main Pi, which must inspect the exact run through the public status/transcript controls so package-owned stale-process reconciliation can run, then steer once or stop and replace the child with a smaller fresh task. A guarded hidden follow-up prevents Main Pi from acknowledging the notice and ending without taking a control action. Empty-output failures are never resumed with their bloated context; useful transcript findings are salvaged into a fresh, narrower replacement.

If a delegated tool call fails and no corrected delegation follows, LemonPi queues one hidden recovery turn requiring Main Pi to diagnose the cause, preserve partial work, and re-delegate the remaining slice when retrying can help.

The extension also handles LemonPi's private RPC control messages for direct child steering and stopping. It validates the target and calls `pi-subagents`' public `subagents:rpc:v1` `steer` or `stop` method, so Command Center intervention reaches the selected background run without an LLM relay or transcript pollution.

Main Pi is the sole owner of user clarification. It uses the required `ask_user_question` tool only when a decision genuinely blocks scope, safety, or the next useful action; discoverable facts and non-blocking preferences do not justify an interruption, and subagents return uncertainty to Main Pi instead of opening competing questionnaires.

For multi-step work, Main Pi maintains the user-visible plan with the required `rpiv-todo` package. LemonPi reads the package's public tool-result snapshot to render native progress above the composer and restores it from the active session after reload, compaction, or session switching. The checklist supplements concise narration rather than replacing it. Todo state remains session-scoped by the package; a child checklist can be surfaced independently when that agent profile explicitly grants the `todo` extension tool.

LemonPi loads `extensions/narration.ts` explicitly for every managed Pi process. It is not installed into the user's global Pi configuration.
