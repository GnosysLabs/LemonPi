# LemonPi narration

First-party Pi extension bundled with LemonPi. It adds visible narration and supervisor/worker orchestration contracts to every Pi turn, compiles concise semantic handoffs into valid `pi-subagents` calls, defaults top-level delegations to background execution, and requests guarded repair responses if a run settles after tool activity without a closing explanation. Delegation recovery and closing-narration recovery are tracked independently, so one cannot accidentally suppress the other.

The async policy uses the public mutable `tool_call` extension hook and the package's existing `async` option. It does not patch or fork `pi-subagents`, and it never invents child wall-clock timeouts. Main Pi is kept interruptible: LemonPi blocks `subagent_wait` and requires Main Pi to end its turn after dispatching and narrating active work. A successful launch or resume, or one authoritative active status result, closes status polling for the rest of that real user turn and injects a final handoff instruction into the next model call; hidden continuation messages cannot reset that guard. Package completion events normally wake integration; Command Center also watches for a run crossing from active into `complete`, `failed`, `stopped`, or `rejected` and sends a delayed private fallback wake. A persisted mission record independently tracks the current phase, active run ids, writer ownership, and next visible task. After reload, session switching, or compaction, LemonPi reconciles those recorded runs directly through the package RPC bridge without waking the model: active work silently restores its listener, terminal work wakes integration once, and paused, needs-attention, or repeatedly unreadable state produces one actionable intervention wake. The five-second idle watchdog then continues only genuinely unowned plan or integration work. This means a missed package notification no longer strands the workflow, while progress/status updates still do not wake Main. A child remains alive between Main Pi turns, so a new user message can receive an immediate supervisor response and be turned into direct steering.

Dispatch is risk- and scope-based rather than file-count-based, but Main Pi is always a read-only orchestrator. Bounded work uses a one-call executor fast path: Main supplies the actual outcome and LemonPi deterministically adds execution mode, chunk boundaries, acceptance defaults, async behavior, and the initial child checklist. Broader work is divided into independently reviewable vertical chunks with real dependencies. A dependency-ready wave may contain up to four implementation workers when their write surfaces are disjoint; otherwise chunks remain sequential. Parallel lanes still require Main's semantic judgment about exact repo-relative owned paths; LemonPi supplies worktree isolation, no-dependency declarations, artifact capture, and the concurrency cap. LemonPi intentionally does not hard-code a provider, model, or custom specialist name.

Role selection remains dynamic without imposing discovery ceremony on ordinary work. The built-in worker is the immediate default for a bounded implementation. Main calls `subagent({ action: "list" })` only when a custom or specialist capability may materially improve the result, then selects from the package's executable roster by exact runtime name and description. Planner is reserved for architecture, ordering, or ambiguity that brief inspection cannot resolve; it is not a prerequisite for multi-file coding. Every specialist must answer a concrete question that changes the next decision. The compiler infers read-only intent for known analysis roles and explicit read-only language, and implementation intent for workers and implementation requests; an explicit `Execution mode:` declaration still wins.

Main Pi cannot impose per-dispatch wall-clock, turn, tool, or usage budgets. LemonPi strips `timeoutMs`, `maxRuntimeMs`, `turnBudget`, `toolBudget`, and `usageBudget` from generated single, chain, and parallel launches before `pi-subagents` validates them. Work is bounded through task decomposition and activity-based intervention instead of guessed counters. Budget defaults deliberately configured by the user in package settings or an agent profile still apply because they are resolved by `pi-subagents` after the sanitized call.

Every new delegated task and revival receives a child checklist before launch. Main may author two to five meaningful milestones when they add value; otherwise LemonPi generates one outcome-level item automatically. LemonPi equips discovered agents with a child-only `child_todo` bridge backed by `rpiv-todo`, preserving Main Pi's normal `todo` provider, all unrelated ambient extensions, and existing overrides. The bridge registers the child tool and store inside one module graph, initializes each attempt's checklist before the first model request, and persists a uniquely identified machine-readable seed in the child transcript; later real `child_todo` results supersede that seed during resume, compaction, and tree replay. A revival seed immediately replaces the previous attempt's completed list and is rebound to the exact child owner. Children advance those existing task ids as outcomes are verified rather than spending time inventing a plan, batching updates, or treating a future final response as already complete. Command Center presents the data simply as Tasks, filters by owner, and only labels an active child `finalizing` when its todo snapshot is newer than that attempt's start time. Legacy children without a seed retain the one-time reminder fallback.

The extension mechanically blocks Main Pi's file-editing tools and common shell-based project mutations while leaving inspection, search, tests, builds, status checks, and git-management operations available. The only source-mutation exception is a tightly parsed `git apply` command targeting a package-generated patch under `.pi-subagents/artifacts/worktree-diffs/`; arbitrary patch paths, shell composition, redirects, and unsupported options remain blocked. Any executable agent selected from the live roster may own an implementation chunk when its declared role matches; LemonPi applies the same bounded chunk and isolation policy without keying behavior to that agent's name. Corrections should steer or resume the same writer whenever possible.

Reviewers and other specialists are optional tools, not pipeline stages. An independent reviewer requires an explicit user request, a material risk boundary, or a concrete `Review justification: ...`; LemonPi mechanically blocks ceremonial review calls and blocks a second reviewer pass unless the user explicitly requested multiple reviews. Delegations without explicit runtime verification disable `pi-subagents`' automatically inferred structured acceptance report because Main Pi owns integration and validation. Only blocker-level findings justify a repair pass, and Main Pi validates that repair directly instead of creating a review-repair-review loop.

Acceptance configuration is preflighted before a worker launches. LemonPi opts every managed delegation into `pi-subagents`' generic agent contract v1, which keeps execution success separate from acceptance, review, and observed file-mutation effects. Read-only tasks are additionally reinforced with an unambiguous no-file-mutation instruction before launch, so a planning artifact cannot fail merely because it made no edits. LemonPi defaults unspecified acceptance to `none` so `pi-subagents` cannot infer a post-run gate that Main Pi did not configure. Explicit `verified` acceptance is allowed only with at least one well-formed runtime `verify` command; merely asking the worker to run tests or report validation does not satisfy the package API. A malformed verified contract is blocked immediately without consuming a worker run.

The runtime permits one writer in the shared checkout or one active parallel wave of at most four writers in package-managed isolated worktrees. Parallel implementation is accepted only as explicit top-level tasks; every lane must declare `Owned paths:`, and parent/child path overlap is rejected before launch. LemonPi automatically enables worktrees, adds `Depends on: none`, caps concurrency at four, and forces artifact capture. Because `pi-subagents` requires a clean source checkout before creating worktrees, Main Pi checks status first and falls back to sequential work when user changes are present instead of stashing, committing, or discarding them. Writer-wave ownership is released from `pi-subagents`' structured `subagent:async-complete` lifecycle event keyed by the exact run id; human-readable completion text is only a compatibility fallback.

On completion, `pi-subagents` captures every temporary worktree as a patch, removes its worktree and branch, and exposes a versioned `parallelHandoff.path`. Main Pi reads that manifest, verifies the base commit, child status, patch health, and owned-path boundary, then integrates accepted patches one at a time with a guarded check/apply sequence. A failed or conflicting lane does not erase successful independent work and does not cause the entire wave to rerun. After integration Main Pi validates the combined checkout, reports the checkpoint, and dispatches the next dependency-ready wave. Two consecutive failed waves stop automatic retries so repeated failure becomes an explicit blocker instead of an invisible loop.

`needs_attention` is treated as an intervention request rather than a healthy running state. The package wakes Main Pi, which must inspect the exact run through the public status/transcript controls so package-owned stale-process reconciliation can run, then steer once or stop and replace the child with a smaller fresh task. A guarded hidden follow-up prevents Main Pi from acknowledging the notice and ending without taking a control action. Empty-output failures are never resumed with their bloated context; useful transcript findings are salvaged into a fresh, narrower replacement.

If a delegated tool call fails and no corrected delegation follows, LemonPi queues one hidden recovery turn requiring Main Pi to diagnose the cause, preserve partial work, and re-delegate the remaining slice when retrying can help.

The extension also handles LemonPi's private RPC control messages for direct child steering and stopping. It validates the target and calls `pi-subagents`' public `subagents:rpc:v1` `steer` or `stop` method, so Command Center intervention reaches the selected background run without an LLM relay or transcript pollution.

Main Pi is the sole owner of user clarification. It uses the required `ask_user_question` tool only when a decision genuinely blocks scope, safety, or the next useful action; discoverable facts and non-blocking preferences do not justify an interruption, and subagents return uncertainty to Main Pi instead of opening competing questionnaires.

For multi-step work, Main Pi maintains the user-visible plan with the required `rpiv-todo` package. LemonPi reads the package's public tool-result snapshot to render native progress above the composer and mirrors its next unfinished item into the durable mission state. If Main settles with unfinished work and no live delegation, or a child reaches a terminal state without a successful integration wake, the scheduler resumes Main. It does not wake for ordinary todo updates or while a child is active. After three ignored continuation attempts it pauses the mission, preventing an infinite loop. The UI also derives animation from the authoritative Main/subagent lifecycle, so persisted intent cannot look actively running while every agent is idle. The checklist supplements concise narration rather than replacing it. Todo state remains session-scoped by the package; the bundled child bridge seeds each delegated session without copying Main Pi's plan into the child's state.

LemonPi loads `extensions/narration.ts` explicitly for every managed Pi process. It is not installed into the user's global Pi configuration.
