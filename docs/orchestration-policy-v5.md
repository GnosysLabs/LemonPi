# Orchestration policy v5

Policy v5 makes latency and child-run cost enforceable runtime behavior.

## Direct fast path

One-repository ordinary UI work affecting one to five low-risk files is performed directly by Main Pi. It has no worktree, delegation, complete-roadmap gate, reviewer, wave validation, or final holistic validation. It receives one implementation pass and one focused check. A local UI request cannot silently expand into backend, protocol, synchronization, or cross-platform work.

## Child execution

Every child launch receives runtime-owned hard limits. Read-only defaults are 60,000 tokens, 8 turns plus 2 grace turns, 25 tool calls, and 10 minutes. Implementation defaults are 120,000 tokens, 12 turns plus 2 grace turns, 45 tool calls, and 15 minutes. The `LEMONPI_READONLY_*` and `LEMONPI_IMPLEMENTATION_*` environment variables can lower or raise individual limits.

LemonPi refreshes authoritative token, turn, tool-call, transcript, activity, and elapsed-time metrics every five seconds. Reaching any hard ceiling stops the exact run and preserves its partial output for integration or a smaller fresh replacement. Routine repository reconnaissance is routed to the read-only scout at low reasoning. Normal workers use medium reasoning; material security, privacy, migration, concurrency, release, or protocol work uses high. Main Pi runs medium by default and moves to xhigh only for an explicit architecture, migration-strategy, security-model, or protocol-design decision.

## Deterministic integration

`lemonpi_git integrate_worker_result` accepts the exact completed run ID. It reads the versioned handoff manifest generated by `pi-subagents`, verifies run identity, repository identity, base revision, patch ownership, and changed paths, then applies, stages, checks, and commits the patch. A second model never copies an already-completed patch. `integrate_worktree` remains the inspected fallback for a prepared registered worktree. Clean integrated worktrees are removed after the relevant focused validation passes.

## Dispatch and recovery

Dispatch preflight canonicalizes abbreviated revisions, ignores a base revision that has no worktree, verifies prepared worktrees at their full resolved commit, and generates a valid deterministic recovery branch when a proposed checkpoint branch is missing or invalid. Preflight deferrals do not trigger delegated-failure recovery. Only a failed launch does. A corrected resume re-reads authoritative terminal state before applying correction rules.

After two failures of the same LemonPi tool contract, Main Pi takes the named safe fallback. It does not spend another turn renegotiating malformed internal parameters.

## Mission state and task history

Mission snapshots use a stable content hash that excludes timestamps. Identical changes are skipped and rapid distinct changes are coalesced into one durable append. Completion wakes are queued only after Main Pi's current turn and tools settle.

Simple work needs one to three meaningful todo items. A dispatched lane may own one `todoId`; LemonPi updates it on start, completion, failure, and stop. Mission todo history is append-only: corrections and superseding work are appended instead of deleting the original record.

## Review and validation reuse

Review evidence is keyed by repository, revision, diff hash, and scope. Rewording a risk justification does not commission a duplicate review. Validation evidence is keyed by repository revision, diff hash, command, relevant paths, and dependency state; scope-label changes do not rerun an unchanged suite. Run one focused check per slice and one broader check only after a genuinely multi-slice integration.
